1.개요

2024년 3월부터 5인 규모 아웃소싱 회사에서 프론트엔드를 맡고 있습니다. 기술 선택과 초기 세팅부터 배포, 운영, 인수인계까지 한 사이클을 열네 번 돌렸고, 그중 넷은 기여도 100%입니다. 대표 작업은 2년 4개월째 운영 중인 골프 티켓 예매 플랫폼 eticket, 넉 달 만에 페이지 130개를 사실상 혼자 완성한 AI 상담 플랫폼 onui, 앱스토어와 플레이스토어에 출시한 쓸모, 2024 스마트앱어워드 대상을 받은 L.Scan입니다.

프론트엔드를 혼자 맡다가 둘이 된 환경에서 일해 왔습니다. 그래서 어느 한 단계만 떼어 맡은 경험이 없습니다. 기술 선택과 초기 세팅을 직접 하고, 개발을 거쳐 배포와 운영까지 가고, 끝난 프로젝트는 인수인계까지 했습니다. 법인 설립부터 함께한 1호 직원이고, 회사가 TIPS 2024와 청년사업패키지, 재도전패키지에 선정되는 과정에서 연구 노트 작성과 심사 제출용 웹 애플리케이션 제작을 맡았습니다. 사업계획서를 쓰거나 선정을 주도한 것은 아닙니다.

외주 환경이라 도메인의 폭이 넓습니다. 골프 티켓 예매와 전문가 상담, 중장년 채용, e스포츠 대회, 건설 업체 연결, 모임 플랫폼, 인플루언서 광고 매칭, B2B 상품 관리, 제품 안전 점검까지 겹치는 영역이 거의 없습니다. 처음 보는 업무 규칙을 빠르게 파악해 화면으로 옮기는 일을 반복해 온 셈입니다. 반대로 한 서비스를 오래 파고든 경험은 eticket 하나에 몰려 있습니다.

반면 최근 스택은 한 지점으로 모였습니다. 2026년에 시작한 onui, more, populers 세 프로젝트의 의존성이 Next 16, React 19, TanStack Query 5, Jotai, Zod 4, Tailwind 4로 거의 같습니다. 우연이 아니라 팀 표준을 세워 재사용한 결과입니다.

2.강점

2.1.한 사이클을 열 번 넘게 돌렸습니다

혼자 100%를 쓴 프로젝트가 넷입니다. PUBG가 67커밋, 한국 중장년 협회 사이트가 31커밋, 쓸모 앱이 48커밋, 그리고 onui는 434커밋 중 432개를 썼습니다. 여기에 직접 세팅한 eticket과 커넥티드456이 각각 1,173커밋과 728커밋으로 붙습니다.

이 축의 핵심은 속도입니다. onui는 넉 달에 페이지 130개를 사실상 혼자 끝냈고, PUBG는 대회 시작 일주일 전에 착수해 일주일 만에 MVP를 실서버에 올렸습니다. 썸띵은 두 달 만에 297커밋을 넣었습니다.

2.2.AI를 제품 기능과 업무 방식 양쪽에 넣어 봤습니다

대부분은 둘 중 하나만 갖습니다. 양쪽을 해 본 것이 차별점입니다.

제품 쪽은 onui입니다. 상담 챗봇과 사전 체크리스트 생성, 음성을 텍스트로 바꿔 만드는 상담 요약, 전문가 리포트 초안, 비식별 사례를 쌓아 유사 사례를 찾는 검색까지 상담 흐름 전체에 배치했습니다. more에서는 모임 소개글을 읽고 성향 질문을 만든 뒤, 호스트와 참여자의 답을 비교해 매칭률을 냅니다.

업무 쪽은 관리자 페이지 생성 워크플로우입니다. 공통 컴포넌트를 먼저 만들어 두고, 화면 목록과 유저 플로우를 정리한 문서를 모델에 넘겨 CRUD 뼈대를 받은 뒤 고유 기능을 얹습니다. 예전에는 관리자 페이지 하나에 짧으면 일주일, 길면 한 달이 걸렸는데 지금은 2~3일이면 끝납니다.

2.3.반복을 재사용 가능한 자산으로 바꿔 왔습니다

유틸을 프로젝트마다 다시 쓰는 피로감에서 사내 라이브러리 @freewier2/things가 나왔습니다. 템플릿에 넣는 대신 npm private으로 배포해, 템플릿을 쓰지 않는 프로젝트에서도 설치만으로 쓸 수 있게 했습니다. 여기서 한 발 더 나간 것이 Swagger 코드 생성 커스텀 템플릿입니다. 프로젝트 셋업에 하루가 걸리던 것이 지금은 한 시간 안에 끝납니다.

2.4.웹과 앱을 모두 실제로 출시해 봤습니다

쓸모는 같은 서비스를 웹과 앱으로 만들어 앱스토어와 플레이스토어에 배포했고, L.Scan은 웹을 하이브리드로 패킹해 앱으로 냈습니다. 두 경험을 React Native 템플릿으로 정리해 웹뷰 설정과 자주 쓰는 네이티브 기능을 재사용할 수 있게 했습니다.

3.1.eticket — 골프 티켓 예매 플랫폼

골프 대회 일정을 알리고 티켓을 팔며 행사도 여는 서비스입니다. 주 사용자는 골프를 즐기는 중년층이고 회원 계정은 6,591개입니다. 입사 후 처음으로 초기 세팅부터 맡은 프로젝트이자, 가장 오래 붙어 있는 프로젝트입니다. 프론트엔드는 세 명이 거쳐 갔습니다. 본인 1,173커밋, 동료 479커밋, 중도 퇴사자 406커밋입니다.

개발 차수

1차는 2024년 6월부터 11월까지 515커밋으로 초기 세팅과 MVP, 예매·결제 흐름을 만들었습니다. 2차는 2025년 2월부터 9월까지 289커밋으로 기능을 확장하고 관리자 페이지를 재정비했고, 3차는 2026년 1월부터 4월까지 369커밋으로 이미 끝났습니다. 이후는 운영 대응 위주입니다.

예매 밖의 운영 기능

대회 현장에서 쓰는 전광판 실시간 추첨을 소켓으로 만들었습니다. 대회 운영 화면에서 추첨을 돌리면 현장 전광판에 결과가 바로 나갑니다. 해외 관객을 위해 PayPal 결제를 붙였고, 템플릿을 내려받아 명단을 채워 올리면 초대권 성격의 티켓을 대량 발송하는 기능도 넣었습니다.

처음 세팅한 프로젝트라서 생긴 빚

처음 만든 만큼 초반 코드에 가독성과 성능이 아쉬운 부분이 남았고, 추가 개발을 할 때마다 그 위에 쌓이는 구조였습니다. 리팩터링을 따로 잡는 대신 기능을 더할 때 해당 영역의 레거시를 함께 정리하는 방식으로 갔습니다. 대규모 정리를 거치면서 결제처럼 중추가 되는 기능에서 불안정성을 걷어냈습니다.

요구사항도 계속 움직였습니다. A라는 조건으로 좁혀 만든 기능에 변경이나 추가 요청이 들어오는 일이 반복됐습니다. 그래서 변경 작업을 할 때마다 당장의 요구만 맞추지 않고 확장 가능한 구조로 바꿔 두었고, 이후 추가 개발이 눈에 띄게 수월해졌습니다.

운영 중 에러를 사후에만 알 수 있던 구조

프로덕션 에러를 클라이언트가 직접 겪거나 CS로 접수된 것만 보고받았습니다. 로그를 계속 들여다보지 않는 한 실사용자가 겪은 에러를 제때 잡을 방법이 없었습니다.

Sentry를 붙이고 Slack 알림을 연결했습니다. 발생 즉시 인지가 가능해진 것도 컸지만, 더 큰 변화는 제보의 해상도였습니다. "A 기능이 안 된다"는 모호한 말을 받아도 어떤 API에서 어떤 에러가 났는지와 사용자의 행동 기록까지 함께 볼 수 있게 되면서 이슈 처리가 훨씬 수월해졌습니다.

관리자 페이지의 컨벤션 불일치

관리자 목록 페이지들은 UI가 획일화되어 있었지만 개발 시기와 담당자가 달라 컨벤션이 어긋나 있었고, 그 탓에 실제 동작이 페이지마다 달라지는 경우가 있었습니다. 342줄짜리 docs/admin-state-convention.md를 쓰고 리팩터링할 때 이 문서를 기준으로 목록 페이지를 다시 만들었습니다. 뒤에 나올 문서 기반 관리자 페이지 작업의 출발점이 된 작업입니다.

Pages Router를 고른 이유
당시 대부분의 프로젝트를 Pages Router로 작업하고 있었습니다. 새 기술을 성급히 들이기보다 이미 완전히 통제할 수 있는 아키텍처로 안정성을 확보하는 쪽을 택했습니다. 지금도 마이그레이션 계획은 없습니다.

3.2.onui — AI 기반 전문가 상담 플랫폼

특정 분야 전문가에게 상담을 받는 서비스입니다. AI 챗봇과 대화하거나 성향 질문에 답해 전문가를 추천받고, 대면과 전화, 화상 중에서 고릅니다. 전문가는 세미나도 열 수 있는데 상담과 달리 티케팅 방식에 가깝습니다.

화상 상담을 직접 만들었습니다

외부 화상 SDK에 기대지 않고 LiveKit을 자체 호스팅했습니다. 화상 통화와 화면 공유, 채팅, 음성의 텍스트 변환, AI 분석을 한 상담 세션 안에 담았습니다.

LLM과 RAG를 상담 흐름 전체에 배치했습니다

기능 입력 산출과 쓰임
AI 챗봇 선택한 분야 + 이용자 질의 참고용 상담 답변, 같은 대화로 전문가 추천
사전 체크리스트 상담 주제, 직전 답변 꼬리를 무는 사전 질문, 매칭과 상담 신청의 참고 자료
상담 요약 화상 음성의 텍스트 기록 이용자·관리자가 다시 보는 상담 노트
리포트 초안 상담 기록 핵심 요약과 조언 초안 → 전문가 검토 후 최종 리포트
유사 사례 검색 비식별 상담·문답 DB 답변 근거, 비슷한 실무 사례 제시

넉 달에 130페이지가 가능했던 이유

세 가지를 겹쳤습니다. 템플릿으로 초기 세팅과 공통 컴포넌트, 훅의 공수를 줄였고, 템플릿에 넣기엔 너무 국소적인 코드는 다른 프로젝트와 개인 코드베이스에서 가져왔습니다. 그리고 관리자 페이지는 문서와 규칙 기반 AI 워크플로우로 처리했습니다. 셋 중 공수가 가장 크게 줄어든 것은 세 번째입니다.

캐시가 남아 사용자 경험을 망치던 문제

react-query 전역 캐시 설정 탓에 등록이나 수정 뒤에도 이전 캐시가 남았습니다. useMutation을 useApiMutation으로 감싸 갱신할 쿼리 키를 선언하게 만들고, 페이지나 컴포넌트에서 invalidateQueries를 직접 부르지 못하도록 규칙으로 고정했습니다.

쿼리 키 규약도 손봤습니다. 기존에는 useGetChatMembers를 쓰면서 키는 ['members','chat']이라 훅 이름과 키가 어긋나 헷갈렸습니다. 훅 이름에서 use만 뗀 getChatMembers 형태로 통일해 초기화할 쿼리를 명시적으로 지정할 수 있게 했고, 이 규칙을 팀 AI 규칙 파일에 적어 같은 실수가 반복되지 않게 했습니다.

3.3.커넥티드456 — 중장년 취업·교육 플랫폼

구직자와 기업을 매칭하고 채용 공고를 올려 중장년 채용을 돕는 플랫폼입니다. 라운지에서 취업과 생활 정보를 제공하고 커뮤니티와 이벤트도 운영합니다. 부트캠프는 플랫폼에서 신청을 받고 관리자 페이지에서 명단을 관리합니다. 본인 커밋 수로는 eticket 다음으로 큰 프로젝트입니다.

PC와 모바일을 라우트에서 갈랐습니다

중장년 대상이라 PC와 모바일의 UI 차이가 컸고, 클라이언트가 반응형이 아닌 적응형을 명시해 요청했습니다. 한 컴포넌트 안에서 분기할 수도 있었지만 스파게티 코드가 될 가능성이 보였습니다. src/pages/[userAgent]/ 라우트로 과감히 나누고 PcMain과 MobileMain을 따로 렌더링했습니다. 유지보수 비용이 적지는 않았지만, 한 컴포넌트에 둘을 섞었을 때를 가정하면 그래도 적은 쪽이었다고 봅니다.

글자 크기를 사용자에 맞춰 다시 잡았습니다

처음에는 다른 프로젝트와 같은 표준 폰트 크기로 개발했습니다. 이후 중장년 사용자를 고려해 기본 폰트를 16px에서 18px로 키우고, 다른 요소의 크기도 눈에 잘 들어오면서 전체 균형은 유지되도록 다시 조정했습니다.

가장 기억에 남는 프로젝트

프론트엔드 두 명으로 시작했는데 한 명이 중도에 퇴사했습니다. 한동안 혼자 진행하다 새 팀원이 합류했지만, 기획의 규모가 크고 히스토리를 따라가기 어려워 실질적인 작업은 거의 혼자 했습니다.

초기 세팅과 MVP를 맡았고, 2차 개발에서 넘어온 이력서 페이지는 버그가 많아 아예 새로 만들었습니다. 설 연휴를 반납하고 버그를 잡은 적도 있습니다. 히스토리가 끊긴 코드를 떠안아 안정화까지 끌고 간 시간이 길었던 만큼 가장 기억에 남는 프로젝트입니다.

국민건강보험 API를 연동해 자격과 경력 확인에 필요한 정보를 받아 왔고, 인증 UI는 외부 위젯 대신 직접 만들어 붙였습니다. PWA는 클라이언트가 하이브리드 앱 대신 모바일 브라우저의 홈 화면 추가를 앱처럼 쓰고 싶어 해서 넣었습니다. 이력서 PDF는 회원 ID를 서버에 넘겨 서버가 만든 문서를 프론트엔드에서 내려받는 방식입니다. 자매 서비스로 한국 중장년 협회 사이트가 있습니다. 2025년 7월에 2주 동안 31커밋을 혼자 작성했습니다.

웹을 중심에 두고 네이티브는 앱 전용 기능만

3.6.more — 모임·클래스 플랫폼

사용자가 모임을 열거나 참여하는 서비스입니다. 일일 모임과 정기 모임이 있고, 전문가 인증을 받은 사용자는 클래스를 열 수 있습니다. 클래스는 호스트가 참여자에게 정보를 제공하는 방식이라는 점에서 일반 모임과 다릅니다.

서비스의 중추가 채팅에 몰려 있습니다

모임마다 단체 채팅방이 열리고 필요하면 1:1 채팅도 가능합니다. 채팅방 안에 위치 공유와 1/N 정산, 일정 변경 투표, 미디어 전송이 들어 있어 서비스의 핵심 기능 상당수가 채팅에 모여 있습니다. 그래서 특히 신경 써서 작업했습니다.

WebSocket과 STOMP로 구현하고 관련 로직을 useSocket.ts 커스텀 훅으로 묶어 연결과 연결 상태, 해제, 구독, 발행을 반환하는 형태로 정리했습니다. 도배와 외부 거래 유도, 개인정보 유출을 막는 정규식 가드도 넣었습니다.

모임 등록 때 AI가 성향 질문을 만듭니다

모임을 등록하는 시점에 AI가 모임 소개를 읽고 돈과 시간, 분위기, 뒷풀이처럼 분야별 질문을 생성합니다. 호스트는 각 질문에서 자신이 선호하는 답을 미리 고릅니다. 나중에 참여자가 같은 질문에 답하면 두 답을 비교해 매칭률이 나옵니다. 모임 관리 화면에서는 질문을 새로 만들지 않고 호스트가 골라 둔 선호 답만 수정합니다.

3.7.L.Scan — 제품안전 셀프체크

롯데중앙연구소 안전센터가 기획하고 자사가 개발한 제품안전 셀프체크 앱입니다. 롯데 유통사에서 파는 상품의 라벨을 카메라로 찍으면 안전인증 정보와 신고 내용을 확인할 수 있습니다. 스토어에 공개하지 않은 사내 업무용 프로그램이며, 웹으로 만들어 하이브리드로 패킹해 앱으로 냈습니다.

심사에서는 OCR과 정부 OPEN API를 연동해 복잡한 인증번호 확인 절차를 줄인 점, 여러 인증번호를 촬영 한 번으로 판정하는 효율성, 불필요한 요소를 줄인 직관적인 화면이 평가받았습니다. 사내 업무용임에도 기술적 혁신성과 현장 업무 기여도를 인정받은 결과입니다. 수상은 서비스 전체에 대한 것이고, 맡은 영역은 아래 관리자 페이지와 사용자 화면입니다.

관리자 페이지 — 화면과 API를 처음부터 붙였습니다

레이아웃과 메뉴부터 만들었습니다. 사이드 탭과 라우트, 그리고 목록과 상세에서 공통으로 쓰는 틀인 테이블과 페이지네이션, 정보 카드를 잡았습니다. 관리자 로그인과 로그인 가드를 넣고, 토큰 없이 보내야 하는 로그인 요청을 위해 인증을 건너뛰는 처리를 뒀습니다.

대시보드는 기간 조회와 품목별 유효·비유효 집계, 추이 차트를 API와 연결했습니다. 요청 목록은 목록과 필터, 상세를 연동하고 품목과 제품명 컬럼을 더했습니다. 품목 목록은 전기용품과 생활용품, 어린이용품, 화학제품, 전파적합성 다섯 가지를 목록과 상세로 붙이고 기록 삭제와 외부 인증 검색 링크를 넣었습니다.

운영 관리에서는 환경 설정에 담당자와 인증코드, 월별 OCR 한도를 두고 공지와 이용가이드의 등록, 수정, 삭제를 연동했습니다. 목록 필터 결과를 엑셀로 받는 API도 연결했습니다. 조회 조건은 URL에 고정해 새로고침이나 공유에도 유지되게 했고, 시간 표시는 한국 시간으로 맞췄습니다.

사용자 화면 — 같은 조회 결과를 쓰는 쪽을 다듬었습니다

조회할 파일을 고르는 흐름을 추가하고, 결과 요약의 유효성 판정과 상세 화면, 결과 완료 상태를 고쳤습니다. 이력 보기 화면의 로딩과 동작을 수정하면서 푸터에 하드코딩된 값을 제거했고, 처리 결과를 알리는 토스트를 넣었습니다. 시스템 공지 노출과 공지·이용가이드로의 이동도 손봤습니다. 로그인 화면에서는 관리자 하드코딩을 빼고 실패 문구를 바꿨으며, 조회 요청에 기기 키를 붙였습니다.

3.8.썸띵 — B2B 상품 관리 시스템

2025년 9월부터 11월까지 두 달 동안 297커밋을 작성했습니다. 전체 644커밋 중 46%입니다. 프로젝트 자체는 3월에 시작했지만 본인은 9월에 합류했습니다. TypeScript 파일은 195개입니다.

직원 25~50명 규모의 썸띵코퍼레이션에서 스프레드시트와 파워포인트로 하던 내부 업무를 하나의 시스템으로 묶는 프로젝트입니다. 상품과 SKU, 옵션, 공급사 관리에 비교 화면이 붙습니다.

엑셀로 처리하던 작업과 상품을 업로드해 쓸 수 있게 하는 기능을 만들었습니다. 대용량 파싱과 검증이 도는 동안 로딩 상태와 화면 표시를 확실히 처리해 이중 클릭 같은 실수를 막았습니다. UX 회의를 여러 차례 거쳐, 기존 업무 방식은 유지하면서 필요한 부분만 더하는 쪽으로 갔습니다.

eticket에도 비슷한 기능이 있습니다. 템플릿을 내려받아 정보를 채워 올리면 해당 고객들에게 초대권 성격의 티켓을 대량 발송합니다. 같은 패턴을 다른 도메인에 한 번 더 구현해 본 셈입니다.

4.공용 자산

4.1.@freewier2/things — 사내 공용 라이브러리

98커밋 중 51개를 작성했습니다. Vite 라이브러리 빌드에 Storybook과 Vitest, husky를 붙였습니다. 필수 유틸을 프로젝트마다 다시 쓰는 피로감에서 시작했습니다. 템플릿에 넣는 대신 npm private으로 배포해 템플릿을 쓰지 않는 프로젝트에서도 쓸 수 있게 했고, 테스트와 React 생태계를 얹어 커스텀 훅도 함께 배포합니다. 코드를 고쳐 GitHub에 올리고 태그를 만들어 push하면 GitHub Actions가 배포합니다.

하위 호환 사고

useMediaQuery를 만들며 다른 함수를 가져오는 과정에서 Cursor가 기존 함수까지 임의로 바꿨고, 그 함수를 쓰던 프로젝트에서 타입 에러가 났습니다. 되돌린 뒤 breaking-changes.mdc 규칙을 추가했습니다. 라이브러리를 배포한다는 것이 무엇을 책임지는 일인지 알게 된 사건입니다.

Swagger 코드 생성 커스텀 템플릿

생성된 API 클라이언트에 매번 토큰 재발급 로직을 덧붙이던 작업과, 파라미터가 filter로 한 번 감싸지는 사내 GET 규칙에 맞춰 필터를 정리하는 작업을 템플릿 자체에 넣었습니다. 위지윅이 필요할 때는 주 사용자인 관리자에게 가장 익숙한 네이버 스마트에디터를 추천했고, 프로젝트마다 새로 붙이는 반복을 없애려 things-smart-editor로 떼어 냈습니다.

15커밋 전부 본인 작업입니다. 웹뷰 설정과 브릿지, 그리고 자주 쓰는 소셜 로그인과 딥링크, 위치, FCM을 템플릿으로 묶어 다음 작업의 공수를 줄이고 일관된 구조를 주도록 했습니다. 팀 표준으로 두고 피드백을 받아 다듬었습니다. 실제 운영 중인 앱은 쓸모이고, 템플릿은 그 설정을 다음 작업에 재사용할 수 있게 정리한 결과입니다.

4.3.Next.js 프로젝트 템플릿

설계와 방향은 팀원 전체가 함께 잡았고 포함 범위도 같이 정했습니다. 실제 생성과 관리는 동료가 전담했고, 본인은 설계 논의와 사용 피드백 쪽으로 참여했습니다. 이 템플릿으로 시작한 프로젝트가 onui, more, populers 세 개이고 셋업 시간이 하루에서 한 시간 안쪽으로 줄었습니다. 템플릿은 팀 회의를 거쳐 계속 업데이트되고 있습니다.

5.AI를 업무에 적용한 방식

5.1.관리자 페이지 생성 워크플로우

여러 프로젝트를 지나며 관리자 페이지에 겹치는 기능이 많다는 것을 알게 됐습니다. 공지사항과 배너, 유저 관리, 관리자 관리처럼 대부분의 사이트에 있는 것들이고, 필요한 건 간단한 CRUD 규칙 정도였습니다. 어드민 프레임워크라는 것이 존재하는 이유와 같은 맥락입니다.

관리자 페이지는 화려한 디자인보다 사용성이 중요하다고 보고 직관적인 구조를 먼저 짠 뒤, 그에 맞는 사이드바와 필터, 상세 페이지, 기본 레이아웃 규칙을 컴포넌트로 만들어 둡니다. 그다음 각 프로젝트의 사용자 화면 목록과 유저 플로우, 기획을 정리한 문서를 AI에 넘기면 기본 CRUD 관리자 페이지가 나옵니다.

IMAGE 10
워크플로우 다이어그램
공통 컴포넌트 준비 → 화면 목록·유저 플로우 문서 작성 → AI가 CRUD 뼈대 생성 → 프로젝트 고유 기능 추가 → 디테일 보정. 각 단계 아래 소요 시간을 적고, 전후 비교(1주~1달 → 2~3일)를 함께 넣으면 설득력이 올라갑니다. 1400×400 가로형.

onui를 예로 들면 상담과 세미나 목록, 공지사항, 배너, 유저 관리, 구독과 광고 결제 목록이 만들어집니다. 여기에 상담 신청 승낙과 세미나 개최 승낙, 세미나 취소 요청 승낙처럼 그 프로젝트에만 있는 기능을 더합니다. 이렇게 뼈대를 잡고 디테일만 손보면 2~3일이면 끝납니다. 예전에는 짧아도 일주일, 길면 한 달까지 걸렸습니다.

5.2.디자인과 개발의 순서를 뒤집은 사례

이 방식으로 관리자 페이지를 만들면 클라이언트에게 보여 줄 디자인 시안이 없습니다. 원래는 시안을 공유하고 의견을 받아 고친 뒤 개발을 시작하는데, 이 흐름을 반대로 돌렸습니다. 프론트엔드에서 MVP를 먼저 뽑고 그것을 피그마로 옮겨 주소를 전달합니다.

웹사이트를 피그마로 옮기는 데는 동료가 만든 도구를 적용했습니다. Playwright로 PC와 태블릿, 모바일의 전체 페이지와 모달을 캡처해 피그마 플러그인으로 올리는 도구이고, 설정 파일만 갈아 끼우면 다른 프로젝트에도 쓸 수 있습니다.

onui에서 이 흐름을 끝까지 돌렸습니다. 클라이언트가 색상과 특정 컴포넌트의 높이 같은 부분을 지적했고, 수정한 뒤 최종 전달까지 마쳤습니다. 도구를 만든 것은 동료이고, 본인이 한 일은 그 도구를 자기 프로젝트에 적용해 순서를 뒤집은 흐름을 실제로 완주한 것입니다.

5.3.팀 규칙

AI 도입으로 개발자 경험과 생산성을 높이자는 회의에서 규칙이 나왔습니다. 이후 다른 팀원이 그 내용을 기초로 실무를 진행했고 의견을 주고받으며 다듬었습니다. .cursor/rules 일곱 종이 그 결과물입니다.

본인이 직접 더한 규칙은 셋입니다. 앞서 적은 useApiMutation과 쿼리 키 규약, 요청이 없으면 주석을 달지 않는다는 규칙, 그리고 AI가 백엔드에 아직 없는 API까지 프론트엔드에서 억지로 필터를 걸어 처리하는 문제를 막는 규칙입니다. 마지막 것에는 백엔드에 전달할 필요 작업 내용을 따로 정리하게 만드는 절차까지 붙여 팀에 공유했습니다.

5.4.AI를 쓰며 지키는 선

AI가 쓴 코드는 무조건 확인합니다. 양이 많으면 요약을 요구합니다. 확인하지 않은 코드가 쌓이면 나중에 직접 고쳐야 할 때 이해하고 수정하는 데 더 큰 공수가 듭니다. 작은 변경까지 AI에 맡기면 그것대로 낭비입니다. AI가 코드를 쓰더라도 개발자가 이해하고 통제할 수 있는 범위 안에 있어야 하고, 어디까지나 개발자를 돕는 수단이라 주객이 바뀌어선 안 된다고 봅니다.
